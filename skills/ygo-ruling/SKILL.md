# 游戏王判例助手（ygo-ruling）

## 本地数据同步（v1.3.9）

在 QQ Agent 的技能设置中提供「同步卡库」和「同步 Lua 脚本」，显示同步阶段、更新时间、数量与错误。需要支持 `settingsActions` 扩展的 QQ Agent 版本；旧版仍可使用在线工具。

- 卡库使用百鸽公开的 `cards.zip` 与 `cards.zip.md5`，校验未变不重复下载。在线查询失败时使用本地卡名、别名、密码和 CID 检索；本地检索不等同于在线全文搜索，且不包含实时 FAQ。
- Lua 全量更新 ProjectIgnis/CardScripts 与 Fluorohydride/ygopro-scripts，使用已保存的 `scriptProxy` 设置；修改代理后请先保存，再重新打开设置同步。
- 数据仅保存在 `DATA_DIR/ygo-ruling/`，不进入发布包。同步失败保留旧数据；同时最多一个同步任务，关闭弹窗不影响任务。
- 同步只保存与读取 Lua 文本，不执行下载的脚本。Lua 是模拟器实现，不代表官方裁定。

> **这个技能在 QQ Agent 控制台的「技能」页签里显示为一张绿色「生效中」卡片。**  
> 装进 `skills/ygo-ruling/` 即生效，热重载会自动加载。  
> 移植自桌面项目 `yugioh/yu-gi-oh-ruling-helper`（浏览器版判例助手）。

让机器人在群里**查卡 + 回答游戏王（OCG）的规则与判例问题**：不是靠模型背卡，而是先把**卡片原文**和**模拟器脚本**查回来，再据此下结论。

**免 Key、免配置。** 卡库和脚本源都是公开接口。

核心设计有两条：

1. **能确定就直给，不能确定就交给人判断** —— 搜出来的结果如果只有一张（或有完全同名的一张），直接给完整卡面；如果有多张易混的候选，`search_card` 只给一份**不带效果文本的候选清单**，由模型自己判断选哪张、或者把清单转发给用户让他挑。
2. **按用户问什么自动分流** —— 只问"这是什么卡/效果是什么"就只发卡面；问"能不能发动/会不会被无效"这类处理细节才去取 Lua 脚本走判例流程。

## 它凭什么算「技能」而不是「插件」

本项目的判据只有一句话（见 README「扩展」一节）：

> **规则能写死 → 插件（`plugins/`）；要理解人话 → 技能（`skills/`）。**

| 判断             | 能写死吗                    | 所以   |
| -------------- | ----------------------- | ---- |
| 用户问的是哪几张卡？     | 不能，得读语义（可能给简称、民翻、英文、密码） | 交给模型 |
| 这题要不要翻 Lua 脚本？ | 不能，要看问的是不是"处理细节"        | 交给模型 |
| 用户的场景具体指哪一种处理？ | 不能                      | 交给模型 |

插件只能提供 `providers` / `hooks`，**模型看不见**，做出来的东西在群里就是"没反应"。所以这里用 `api.registerTool()` 把取证工具交给模型，由它决定何时查。

反过来，**能写死的事都写死**：卡库查询、脚本抓取、代理轮换、结果缓存、JSON 归一化、名字匹配打分。分工是这个技能的设计核心。

## 四个工具

| 工具（模型看到的完整名字）                 | 作用                                                                                                                                                                    |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ygo-ruling__search_card`     | 按 **卡名 / 简称 / 别名 / 日英文名 / 卡片密码** 搜索。**默认 `detail=auto`：卡库能确定是哪张就直接返回完整卡面；有多张易混候选（或结果太多）时只返回不带效果文本的候选清单**，把甄别交给模型。也可显式传 `detail=list`（强制只给清单）/ `detail=full`（强制给前几张全文） |
| `ygo-ruling__get_card`        | 按卡名或密码**精确取回一张或多张**卡的完整卡面（逗号/顿号/换行分隔）。判例常涉及多张卡，一次取回省轮次。没有完全同名的卡时会**标 ⚠️ 并附带并列候选**                                                                                     |
| `ygo-ruling__get_script`      | 按**卡名（或卡片密码）**&#x53D6;回该卡的 YGO/EDOPro Lua 脚本源码（本地镜像 → official → pre-release → ygopro-scripts），返回源码 + 来源目录页                                                           |
| `ygo-ruling__send_card_image` | 按**卡名（或密码）**&#x628A;这张卡的插图发到群里。参数是卡名、**不是图片地址** —— 地址形如 `pics/<卡片密码>.jpg`，让模型拿到就等于把密码又送回去了。所以"查 id → 拼地址 → 发图"全在工具内部做，模型只知道"发了哪张卡的图"                                  |

> 工具 id 会被加载器自动加 `技能id__` 前缀，所以模型看到的是上面这种完整名字。  
> **所有工具输出都不含卡片密码 / cid**（见下节）—— 要取全文就传**名称**，要取脚本就传**卡名**，闭环照样成立。

### ⚠️ 密码 / cid 对模型不外露（2026-10-05 起）

卡片密码（8 位数字）和 cid 是**内部主键**，一律不让模型看见 —— 否则它会顺口念给用户（实测回复第三条就是「简中叫神鹰羽毛扫，密码18144506」这种废话）。

- 卡面头行只有 `【名称】`，不再有 `密码 xxx · cid xxx`；
- 候选清单只有 `名称 ｜ 类型 ｜ FAQ`，**没有密码**；
- `get_script` 入参放宽为**卡名或密码**：给卡名时它自己查一次卡库把密码解出来（解析不出来就明确让模型先去 `search_card` 或问用户）；
- 脚本返回里的文件名与 raw URL 都带密码，所以只回**来源目录页**（`.../blob/master/official`），不回具体文件地址。例外：脚本正文里偶尔自带注释残片，属极少数，未做处理；
- 密码仍然照常用于**内部**：脚本缓存文件名 `data/ygo-ruling/scripts/c<密码>.lua`、抓取 URL。**只是不给模型看。**

### `search_card` 的四种回应

| 情况            | 回应                  | 模型该怎么做                                       |
| ------------- | ------------------- | -------------------------------------------- |
| 卡库只有 1 条结果    | 该卡**完整卡面**          | 直接用；若标注"没有完全同名的卡"，先怀疑是不是写错了                  |
| 有**唯一一张**完全同名 | 该卡完整卡面 + 其他相近卡的精简清单 | 直接用这张，必要时一句带过其他可能                            |
| 有多张完全同名       | **候选清单**            | 必须问用户（罕见）                                    |
| 没有完全同名、又有多张候选 | **候选清单**            | 自己判断：有明显最符合上下文的就用它并说明按哪张理解；分不清就把清单发给用户选（见下节） |

### 卡面里给模型的信息

```
【灰流丽】
别名：日文：灰流うらら / 英文：Ash Blossom & Joyous Spring
类型：[怪兽|效果|调整] 不死/炎 [★3] 0/1800
效果文本：这个卡名的效果1回合只能使用1次。①：……
官方FAQ条目数：79（有官方问答资料，可提示去查）
```

候选清单则是**一行一张、不带效果文本**（结果多时全给全文会撑爆上下文，而且对"认出是哪张"没帮助）：

```
1. 鹰身女妖的羽毛扫 ｜ [魔法] ｜ FAQ 26
2. 狮鹫的羽毛扫 ｜ [魔法] ｜ FAQ 0
```

- **官方 FAQ 条数**是个有用信号：> 0 说明官方有问答资料，模型会提示用户去查；0 则说明官方没收录。
- 命中的别名会标出来（`｜别名「黑魔导女孩」`），用户才认得出自己说的是哪张。

## 歧义怎么处理（这个技能的重点）

游戏王卡名极容易撞：搜「龙」有 100 条封顶、搜「羽毛扫」有两张、「黑魔导」其实是「黑魔术师」。所以**判定"到底是哪张"这件事本身**交给模型，但工具要把判断所需的材料给足：

**① 完全同名 = 确定。** 判定时会把**所有别名**（简中/MD/民翻/CNOCG/日文/英文/密码/cid）都算进去。实测「黑魔导」精确命中「黑魔术师」（命中它的民间译名），不会被误判成歧义 —— 只看规范名会算成 0 分，这是踩过的坑。

**② 虚词会挡匹配。** 「真红眼的黑龙」在卡库里会命中「真红眼黑龙剑」而不是「真红眼黑龙」。所以结果可疑地少时，工具会用去掉「的/之」等虚词的核心词**补搜一次**。

- ⚠️ 补搜**只在结果确实更准时才采用**（有完全同名，或原本 0 条而补搜至少有一条沾边）。否则卡库对乱码词也会硬吐一张卡出来，会把"没这张卡"答成一张完全无关的卡。
- ⚠️ 补搜**只对含中文的查询**做。对英文名去掉空格（`Ash Blossom` → `AshBlossom`）会搜出乱码记录，比原词更糟。

**③ 模型的动作只有三种**（写在提示词里，优先级从高到低）：

| 情况                                   | 动作                                                                                                                                 |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| 有明显最符合上下文的（系列主角卡、前文刚提过、唯一符合属性/种族/等级） | 用那张的**名称**调 `get_card` 取原文 → 回答，并在回答里点明"我按【XX】理解"                                                                                  |
| 几张都说得通、判断不了                          | **先 `send_card_image` 发最可能那张的图，再用 `send_message` 问**：「你说的是【XX】这张吗？不是的话请给我**完整卡名**（写全称，或直接给卡片密码）。」候选彼此太像时把 2~4 个候选列一行一起发。猜错一张等于整题答错 |
| 候选太多（工具会提示已达 100 条上限）或都不像            | 请用户补信息：系列名 / 属性 / 种族 / 等级 / 卡片种类                                                                                                   |

**④ 明确禁止**：不确定却随便挑一张还讲得像确定答案；或者查完不作声。这两条都写进了提示词。

**⑤ 同分排序：整词命中 > 主名命中 > 卡库顺序**（2026-10-05 加）。  
查「霍普」时卡库给的候选里，「剑斗兽 重斗」（**简中名**是「剑斗兽 霍普洛姆斯」）和「No.39 希望皇 霍普」同为 60 分，原样沿用卡库顺序的话前者排第一 —— 于是发出去的图会是剑斗兽。判据是**查询词是不是候选名里独立的一段**（卡名惯用空格分词）：「希望皇 霍普」里「霍普」自成一段 ✅，「霍普洛姆斯」里只是半个词 ❌。`scoreCard` 只多回报 `exactWord` / `onPrimary` 两个标记，**不改 score 语义**，所以确定/歧义的判定阈值（≥60、=100）完全没动。

### 配图（2026-10-05 起）

图床是 `https://cdn.233.momobako.com/ygopro/pics/<卡片密码>.jpg`（实测老卡/新卡/异画 4 张全部 200、image/jpeg、70~90KB）。`send_card_image` 会**先下载一份 base64 作回退**再交给 `ctx.sender.sendImage({url, dataUrl})`，协议端取不到外网图时自动改用内联。返回值里**不含地址**（地址含密码），只回"【XX】的插图已发出"。

## 提示词片段干了什么

技能带了一段提示词（`skill.json` 的 `prompt.sections`，priority 46），把上游桌面工具的裁定方法论搬进了对话：

1. **什么时候用** —— 有人 @ 到机器人、话里出现疑似卡名（"XX 是什么卡""XX 的效果"）就先查卡再答；问交互处理就走完整判例流程。
2. **先查卡，不要背卡** —— 记错一个字，结论就是错的。
3. **候选不止一张时怎么办** —— 即上面「歧义怎么处理」那三条动作，外加两条禁令（不许硬猜、不许沉默）。**这是本次新增的重点。**
4. **按问法分流** —— 只问卡面 → 只发卡面（QQ 里不要 Markdown 记号）；问处理细节 → 才取 Lua 脚本。
5. **判例回答结构**：Lua 脚本审计 → 文本对照 → 精确回答。精确回答的第一句固定为「对用户这个具体问题：可以 / 不能 / 无法确定。」
6. **分清两件事**：「Lua/EDOPro 模拟器实现」≠「官方 FAQ / 事务局裁定」，不许混着说，也不许编造。
7. **必须真的发出去** —— 本项目里模型的纯文本**不会**发到群里，只有调用 `send_message` 才会。所以提示词明确要求：查证 → 用 `send_message` 发回答（长分析建议分条发；需要用户确认候选时也要发出去）。
8. **「无效」类判定的终审依据是脚本（2026-10-07 起，v1.3.1→v1.3.3 重构）** —— 实测事故：deepseek-v4.1-flash 在 `get_card` 已返回正确卡文（「那个效果无效」）的情况下，回答里把它复述成"只是把那个效果的发动无效"，一字不差地说反了（顺带的规则复述也是反的："发动被无效的效果仍然留在连锁上仍要处理"——恰好颠倒）。上下文只有 2.3 万 token，卡文就在眼前，属模型阅读错误而非上下文过长。
   - 流程漏洞：那次 `get_script` 只对**被问的卡**（西艾萝）调了一次，**施放无效的轩辕十四根本没请求**。而轩辕十四官方脚本 `official/c10604644.lua` 第 96 行就是 `Duel.NegateEffect(ev)`（+ `CATEGORY_DISABLE`），一眼定案。
   - **v1.3.3 重构（按用户要求）**：提示词不再以"逐字抄卡文"为主规则，改为**判例题必须先取脚本**——把所有涉事卡（被问的卡＋施放无效/干扰的那张）用 `cards` 参数**一次传给 `get_script`**（新支持的批量模式，`SCRIPT_BATCH_MAX = 5`，中英文逗号/顿号分隔）；脚本里的确定性判据 `NegateActivation()` = 发动无效、`NegateEffect()` = 效果无效，与卡文复述冲突以脚本为准。"逐字抄卡文"降级为**某张卡确实没脚本时的兜底**（此时回答必须注明"按卡文推的，不是脚本审计"）。
   - `get_script` 批量行为：单卡 `card` 参数向后兼容（输出格式不变）；批量时逐张给块、失败不影响其他张，`isError` 只在"有硬失败（查无此卡/解析失败）且一张都没取到"时为 true；没脚本是正常结果不算 error。
   - 实测 prompt 构成（回应"是不是自带 prompt 过长"）：核心系统提示 ≈1.7k tok + 全部技能片段 ≈3.3k tok + 工具表 28 个 ≈4.2k tok ≈ **固定开销 ~9-10k tok**，其余 ~12k 来自运行时注入与会话历史 —— 不构成"太长看漏最近一条工具结果"的条件。
   - 三张卡脚本可取性实测：炎舞-天玑 `official/c57103969.lua` ✅200、轩辕十四 ✅200、西艾萝-一掷乾坤 `c73090586.lua` ❌official/pre-release 双 404（确实未收录）——所以"没取到脚本"那次的正确归因是"尚未收录"，不是"脚本源没通"。
   - 注意：`Fluorohydride/ygopro-scripts` 也收录脚本（根路径直挂 `c<密码>.lua`），可作为 `ProjectIgnis/CardScripts` 之外的备源。
9. **连锁判定要按「那一刻」的场面推演（2026-10-07 起，v1.3.6）** —— 第二个实测事故：**对方场上唯一怪兽用「解放自身」作代价发动效果 → 我方连锁**。模型忽略了代价在**发动时就已经付掉**，把"对方场上有 1 只怪"的初始场面一路用到了连锁处理，得出"可以展示 5 张"的错误结论。
   - 正确时间线：`C1 零露②发动（解放自身作代价，零露当场进墓）→ C2 天救龙发动（付代价：展示手卡这张卡＋额外同调怪）→ 处理 C2 → 处理 C1`。**处理 C2 时对方怪兽区是空的**（C1 还没处理，零衣/露世都还没登场）。
   - 脚本里的确定性判据（`official/c70088809.lua`，调和之天救龙）：
     ```lua
     function s.rescon(sg,e,tp,mg)
       local b1=#sg==1
       local b2=#sg==3 and sg:IsExists(Card.IsAbleToGrave,1,nil)
       local b3=#sg==5 and sg:IsExists(Card.IsAbleToGrave,1,nil) and Duel.GetFieldGroupCount(tp,0,LOCATION_MZONE)>0
       return b1 or b2 or b3
     end
     ```
     即**可选展示数只有 1 / 3 / 5 张**，而「5 张」（总 6 张 → `reveal_count==6` → `●6只` 破坏）**额外要求发动那一刻对方怪兽区不为空**。对方唯一怪兽以自身为代价解放后再连锁 → 场面已空 → 只能展示 1 或 3 张 → **拿不到 ●6只的破坏效果**（剩下 ●2 特召 + ●4 送 1 只展示的同调怪进墓）。
   - 另一条常被忽略的细节：`●6只` 的处理段 `Duel.SelectMatchingCard(tp,nil,tp,0,LOCATION_MZONE,1,1,nil)` 在对方场上**没有怪兽时选不到目标**，`#g>0` 不成立 → 即使因为别的原因凑到 6 张也不会破坏（"条件在发动时判定、目标在处理时判定"是两层）。
   - 由此固化的规则：① 先写时间线；② **代价在发动时立即支付**；③ **连锁后发先处理（LIFO）**，处理 C2 时 C1 要召唤/破坏的东西都还不存在；④ 条件、可选范围、数量上限、目标是否选得到，全部按「代价支付 / 处理那一刻」求值；⑤ 回答里必须明说依据的场面，题目没交代清楚的先问用户。
   - ⚠️ 结论本身（**不能**拿到 ●6只）与卡文推理一致、与脚本一致；但"可选展示数只能 1/3/5"是**模拟器 `rescon` 的实现约束**，OCG 实务里是否同样禁止"展示 5 张"需要以事务局裁定为准 —— 按本技能一贯口径，回答里要如实区分"脚本这么实现"与"官方裁定如此"。

### 卡库接口的实测行为（设计依据，别再摸黑猜）

- **已经按相关度排好序**，直接取前 N 条即可；返回的 `weight` 字段（100 / 90）可佐证，但**判别力不够**（「灰流」这种部分匹配也是 90），所以判定用的是技能自己的打分。
- **单次最多返回 100 条，没有分页参数**（试过 `page` / `limit` / `size`，都无效）。搜「龙」「英雄」这类词必被截断，工具会提示模型结果可能更多。
- **别名很全**：一条记录里有 `cn_name / sc_name / md_name / nwbbs_n / cnocg_n / jp_name / en_name / id / cid`，实测「黑魔导」正是靠 `nwbbs_n`/`sc_name` 命中「黑魔术师」的。**判定"完全同名"必须遍历所有别名。**
- **偶尔会回空壳记录**（没名称、密码 0）——实测搜英文名时出现过。技能会直接过滤掉，否则模型会把一张不存在的卡当候选。
- 接口本身**偶发抖动**（同一个查询可能这次 0 条、下次 1 条），所以工具在"没搜到"时措辞是「卡库里没搜到」，而不是断言"这张卡不存在"。

### ⚠️ 脚本源需要代理（本机实测）

`raw.githubusercontent.com` 在本机**直连被墙**（约 100ms 直接 fetch 失败）。技能内置代理轮换：

```
https://gh-proxy.com/       ← 实测可用，~1s
https://ghproxy.net/        ← 实测可用，~1s
（最后总会再直连兜底一次）
```

- jsDelivr 对这个大仓库直接返回 **403**，不可用，已排除。
- 代理前缀可在技能设置里改（`scriptProxy`）。
- **通常怪兽一般没有脚本**：实测青眼白龙 `c89631139.lua` 就是 404。这不是故障，工具会明确说明"没有脚本或没取到"，让模型退回文本分析。

### 本地脚本镜像（离线，2026-10-07 起）

```bash
node scripts/sync-ygo-scripts.mjs          # 或 npm run sync:ygo-scripts
```

一次性把两个仓库全部下载解压到 `data/ygo-ruling/scripts-mirror/`：

| 镜像 key         | 来源                                       | 实测份数  |
| -------------- | ---------------------------------------- | ----- |
| `official/`    | `ProjectIgnis/CardScripts` 的 `official/` | 13541 |
| `pre-release/` | 同上 `pre-release/`                        | 135   |
| `ygopro/`      | `Fluorohydride/ygopro-scripts` 根目录       | 12124 |

合计 **25800** 份、**115 MB**。`get_script` 的查找顺序变成 **本地镜像 → 缓存 → 在线**；命中镜像时输出头标「（本地镜像）」，耗时从 ~1s 降到毫秒级、且不消耗网络。

- 脚本可带参数：`--proxy https://ghproxy.net/`（覆盖默认代理）、`--out <目录>`。
- **重复执行即全量刷新**；失败重跑时会复用已下载的 zip（`data/ygo-ruling/.sync-tmp/`）。
- 解压依赖系统 `tar`；Windows 会**优先显式调用 `C:/Windows/System32/tar.exe`**（PATH 里靠前的可能是 Git 自带的 GNU tar，**不能解 zip**），失败再降级到 PATH 的 tar、最后用 PowerShell `Expand-Archive`。
- 跑完写 `scripts-mirror/manifest.json`（各目录份数 + 时间戳），并在控制台抽查 3 张卡是否命中。
- 镜像在 `data/` 下（`.gitignore` 覆盖），**不进版本库、不影响打包**；删掉目录即回到纯在线模式。

## 精简模式（判例轮不带群聊人设，v1.3.7+）

**问题**：普通一轮请求固定带上约 12k 字的群聊系统提示（人设 + 全部技能说明）与约 11k 字的本次输入（角色卡 6.2k + 聊天记录 3.7k + 记忆/表情包/引导），合计约 **23k 字符 —— 其中只有约 16% 跟判例有关**。既费钱，也让模型在噪音里找重点（2026-10-07 那几次判例判错，有不少就是在人设废话里跑偏的）。

**做法**：本技能实现核心能力 `prompt.lean-context`（核心契约见 `doc/extend_development/plugin-development.md` §4.7）。命中时这一轮只发：

- **系统提示 4,399 字符** —— 身份一句话 + 本技能 `skill.json` 里那段判例 playbook（**直接读同一份，不抄第二份副本**，避免两处跑偏）+ 最小工具协议；
- **本次输入 144 字符** —— 最近 `leanHistory` 条对话 + 【当前消息】+ 时间，**不含**角色卡/记忆/表情包/引导说明；
- **工具表**只留 4 个本技能工具 + `send_message` / `get_message_images` / `finish`。

实测 **5,008 vs 14,933 字符（省 66%）**。会话记录、用量统计、中止、重试、留档、发送管道**全部照旧** —— 省掉的只是提示词。

### 什么时候才接管（判定是纯文本启发式，必须保守）

① `reach.addressed` —— 私聊 / 被 @ / 拍一拍我 / 命中关键词（reach 由核心算好，与唤醒判定同源）。
**群里路过的闲聊即使满屏术语也不接管**，人设不会莫名消失。

② 话里要有强游戏王信号，满足**任一条**：

| 规则                 | 例子                                        |
| ------------------ | ----------------------------------------- |
| 提到作品本身             | 游戏王 / OCG / ygopro / edopro / master duel |
| 【】里像卡名            | 【灰流丽】、【青眼白龙】的攻击力                          |
| ≥2 个不同术语           | 怪兽…墓地…取对象…裁定                              |
| 「」『』引用 + ≥1 个术语    | 「青眼白龙」的效果是什么                              |

⚠️ **`【】` 里的内容要"像卡名"**：不在停用词表里（通知/公告/求助/重要/图片/表情包/2026…）、且含中日文字符。
⚠️ **`「」『』` 单独不算信号** —— 实测它们在中文闲聊里就是普通引号（"「今天不想上班」""他回了「好好好」"），
以前当成强信号会**大量误伤**。回归网 `test/ygo-lean-context.mjs` 里 21 条"绝不能命中"的闲聊样本必须保持全绿：
**任何人往判定里加规则都要先跑它**。

### 判错了会怎样（三层兜底）

1. **技能层**：`leanMode: false` 一关，这段代码完全不参与，立刻回到原来的行为。
2. **提示词层**：精简 system 明确给模型留了退路 —— 发现"不是在问游戏王"就调 `finish`，不要硬答。
3. **编排器层**：精简轮**一条消息都没发出来** → 自动用**完整上下文在同一会话**再跑一遍（`session.leanFallback=true`，会话页可见），不会重复收尾。

### 已知的残余窗口

- 一条消息**通过了判定、模型却又自己答了**（没走 `finish`），那这轮的回复语气来自上面的身份一句话，而不是你的群聊人设 —— 不会回退（回退只看"有没有发出消息"）。判定越保守，这个窗口越小。
- 判定是**纯文本**的：编排器同步取值，这一轮里不能去卡库查"这几个字是不是卡名"。本地镜像的 `.lua` 首行只有**日文名 + 英文名**，没有简中名，所以做不了"查卡库式"判定。

## 排错

| 现象                             | 原因与处理                                                                                                                                              |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 技能页显示**红色「加载失败」**              | 鼠标悬停看原因。本技能已用项目自带清单校验器验证过，`problems` 为空                                                                                                            |
| 卡片存在但**灰色「已关闭」**               | 点卡片开启。这是唯一的总开关                                                                                                                                     |
| 群里**完全不回答**                    | 先看「响应档位」——档位太低时普通消息根本不会触发模型；再确认卡片是绿色「生效中」                                                                                                          |
| 机器人的话**只在日志里、群里看不到**           | 这是本项目的固有约定：普通文本输出不会发到群，必须 `send_message`。若提示词未生效，检查技能是否为「生效中」                                                                                      |
| &#x8BF4;**"没搜到这张卡"**           | 换个写法（中文全名 / 日文英文名 / 直接给密码）；去掉「的/之」等虚词；也确认真卡是否收录于百鸽、或卡库是不是刚好抖动了一下                                                                                   |
| 只发了一堆候选、**没给卡面**               | 这是**预期行为**：没有完全同名的卡时故意不给全文，逼模型先确认。想直接看前几张的完整卡面，让模型传 `detail=full`；或把卡片密码直接发给它                                                                      |
| 给了一张**像是不相关的卡**                | 卡库对不存在/乱码的词也会硬吐一张最接近的。工具已经加了门槛（补搜必须有完全同名、或至少有沾边的结果）来挡住这种情况；若仍出现，把原始查询和返回的卡名记下来                                                                     |
| &#x8BF4;**"脚本没取到"**            | ① 先确认镜像里有没有：`ls data/ygo-ruling/scripts-mirror/*/c<密码>.lua`；② 通常是通常怪兽，本来就没脚本；③ 代理不可用——试试在设置里换代理前缀；④ 卡名没解析准（没有完全同名的卡）——工具会明确要求先去 `search_card` 或问用户 |
| 来源行显&#x793A;**「（本地镜像）」但内容是旧的** | 镜像没 TTL、不会自动更新。重跑 `npm run sync:ygo-scripts` 刷新；只想更新单张就删掉 `scripts-mirror/*/c<密码>.lua` 让它回退在线取                                                     |
| 回答里蹦出 **8 位数字 / cid**          | 不该出现。密码已从所有工具输出移除，提示词里也明令不许念。若仍出现，说明是模型自己编的 —— 记下原始卡名与回复，检查是否为旧版本技能（`/api/skills` 看版本应为 1.2.0+）                                                    |
| 查询**一直超时**                     | 调大「联网超时」；确认本机能访问 `ygocdb.com`                                                                                                                      |

排查用日志：`data/logs/qq-agent-YYYY-MM-DD.log` 里搜 `ygo-ruling`。

### 改完提示词怎么验证（判例探针）

```bash
npm run probe:judge -- --dry                  # 只组装提示词，确认规则片段进了系统提示词（0 成本）
npm run probe:judge -- --case chain-field-empty --verbose   # 跑单条用例，打印每轮工具调用
npm run probe:judge                          # 跑全部用例
```

`scripts/ygo-judge-probe.mjs` 用**真实模型**跑 `test/ygo-judge-cases.json` 里的判例：加载真实技能 → 组装真实系统提示词与工具表 → 自跑 tool-call 循环（sender 是假的，只把 `send_message` 的内容录下来）→ 输出模型最终发给用户的原话，并对「结论关键词 / 必需的工具调用 / 是否引用了脚本判据」做粗判。

- ⚠️ **会产生真实模型调用费用**（每条用例 3~5 次），所以故意**不挂 `npm test`**，只在改了提示词、想确认"模型行为有没有真的变好"时手动跑。
- 判定口径保守：`mustCallTools` 缺失 = FAIL；`mustMention`（如 `GetFieldGroupCount`）缺失只 WARN（模型可能只用中文描述同一件事，需人工看）。
- 加新用例就往 `test/ygo-judge-cases.json` 追加一条；每次判例事故修完，都应该在这里留一条回归用例。

## 文件构成

```
skills/ygo-ruling/
  ├── skill.json   清单（id / 权限 / 设置声明 / 提示词片段）—— 加载器读它
  ├── index.js     入口（注册四个工具）—— 加载器读它
  └── SKILL.md     本说明文档（给你和以后的 AI 助手看，程序不解析）

scripts/sync-ygo-scripts.mjs   全量脚本镜像同步（不属于技能加载范围，是运维脚本）
```

> `SKILL.md` **不参与加载**。加载器只认 `skill.json` 和入口 `index.js`。
